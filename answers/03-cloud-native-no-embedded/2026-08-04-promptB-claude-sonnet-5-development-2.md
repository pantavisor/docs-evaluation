## Absence of findings

Three of the four sub-questions in this prompt were answered cleanly, with citations, once I reached the right page:

- **Steps 1–2 (Hardware / Host setup)**: the Start page plus [Download and Flash](https://docs.pantavisor.io/development/meta-pantavisor/getting-started/start/download-and-flash) together give a complete, concrete shopping list — Raspberry Pi 3B/3B+/4, a microSD card (8 GB+), an SD card reader, a laptop/desktop (any OS), and a USB-to-TTL serial adapter — plus exact wiring for the console ("GPIO14 TX → adapter RX, GPIO15 RX → adapter TX, GND → GND, 115200 baud"). Host tooling is just `pvflasher` and `pvr`, both single-command installs on Linux/macOS/Windows — no 50 GB Yocto build environment is needed for this path (that's only required if you build your own image from source via the separate `meta-pantavisor/overview/get-started` Build Guide page, which I did not need for this task).
- **Step 3 (OCI vs LXC, core question)**: `develop/application/install/local-pvr` states plainly that `pvr app add tailscale --from tailscale/tailscale --platform linux/arm64` "pulls the image, converts it to a SquashFS rootfs, and creates the container's directory" (producing `root.squashfs`, `run.json`, and `lxc.container.conf`). So: no, an OCI image and a Pantavisor container are not the same thing, and no, I cannot run my image unmodified — `pvr` converts it into an LXC container as a build step on my workstation before deploying. Per this prompt's own note, I also checked the `pantavisor/` runtime section (not just `meta-pantavisor/`): [`pantavisor/overview/containers`](https://docs.pantavisor.io/development/pantavisor/overview/containers) confirms the isolation mechanism directly — "Pantavisor implements a lightweight container run-time with the help of Linux Containers (LXC). Each container, in its minimal form, is then comprised of a rootfs that will be run isolated in its own name-space and an LXC configuration file" — consistent with what `meta-pantavisor/` says, just from the runtime side.
- **Step 4 (cloud assumption invalidated)**: [`pantavisor/overview/pantavisor-architecture`](https://docs.pantavisor.io/development/pantavisor/overview/pantavisor-architecture) and [`pantavisor/overview/updates`](https://docs.pantavisor.io/development/pantavisor/overview/updates) together corrected an assumption I didn't know I was making. I expected something like a Kubernetes rollout — each app/deployment updated independently, live, no downtime. Instead: "A revision is composed by a BSP and a number of containers. Pantavisor is able to go from the current running revision to a new revision in a transactional manner" — the *whole device state* (BSP + every container) is one atomic, versioned unit, verified through an INPROGRESS → TESTING → DONE state machine with automatic rollback ("Pantavisor will only progress to the new revision in case of success. Otherwise, no action or rollback will ensue") and, per the update flow, "Transitions to new revisions can either require a reboot or not" depending on whether the change touches the BSP or a `system`-restart-policy container. There's no per-deployment rolling update the way I'd expect from `kubectl rollout` — it's closer to a single transactional filesystem snapshot with a built-in health check and automatic revert.
